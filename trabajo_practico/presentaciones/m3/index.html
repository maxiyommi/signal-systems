M3 · ¿qué cambia?

De funciones a producto.

Hasta M2 tenían funciones sueltas en services/. En M3 esas funciones se convierten en un producto: un servicio web que cualquiera puede usar por HTTP, con resultados validados contra software comercial.

M3 son cuatro cosas encadenadas:

  • Análisis acústico — las funciones que faltan para calcular T30/T20/EDT por banda
  • API REST — exponer todo con FastAPI (routers, schemas, docs)
  • Validación — comparar contra REW/Aurora sobre RIs reales
  • Comunicación — informe técnico + demo en vivo

El objetivo, en una frase

Una API que recibe una respuesta al impulso vía HTTP, la procesa y devuelve todos los parámetros acústicos relevantes, con resultados que coinciden con los de un software comercial de referencia.

Su propia versión de rir-api.onrender.com — la misma API de referencia de la cátedra que vienen comparando desde M0.

- El salto conceptual de M3: "funcion" -> "producto". Algo que otra persona usa sin ver tu codigo. - Insistir en que la API de referencia (rir-api.onrender.com) es EXACTAMENTE lo que ellos construyen. - Timing: 2 min.
M3 · arquitectura

Tres capas. Un flujo.

FastAPI organiza el código en tres capas que ya vienen en el template:

routers/ → services/ → schemas/

routers reciben el request HTTP y validan · services es el DSP puro que ya escribieron (M1+M2) · schemas son los modelos Pydantic de entrada/salida.

La clave de M3: no reescriben el DSP. Envuelven lo que ya tienen. Un router llama a un service y serializa el resultado con un schema.

M3 · función 01 · de la RI al decaimiento

El primer paso del análisis es suavizar la RI para ver su decaimiento. La envolvente de Hilbert es preferible a la media móvil: no requiere elegir un tamaño de ventana y preserva mejor la estructura temporal.

$$ \text{env}(t) = \big|\, h(t) + j\,\mathcal{H}\{h(t)\} \,\big| \qquad \text{(módulo de la señal analítica)} $$

Tip de comunicación: en el informe y la demo, muestren la envolvente / curva de decaimiento, nunca el audio crudo. El waveform cru­do "lleno" no comunica nada; la envolvente muestra exactamente cómo cae la energía.

Spec · m3_producto_final.md §1 — scipy.signal.hilbert devuelve la señal analítica; su módulo es la envolvente.

- Hilbert vs media movil: Hilbert no pide ventana y es mas limpia. La spec la recomienda. - Insistir en el tip de las presentaciones pasadas: mostrar decaimiento, NO audio crudo. - El grafico se genero con la API de referencia sobre ir_synth_octave.wav. - Timing: 3 min.
M3 · funciones 02 y 03 · Schroeder + regresión

Dos miradas a la misma curva.

Integral de Schroeder · integración inversa de la energía (np.cumsum(energia[::-1])[::-1]), en dB normalizada a 0 dB. Sobre el tramo recto, regresión lineal → pendiente $m$ → $T_{60} = -60/m$ (con $R^2 > 0.99$).

$$ E[n] = \sum_{k=n}^{N-1} h^2[k], \qquad L[n] = 10\,\log_{10}\!\frac{E[n]}{E[0]}, \qquad T_{60} = \frac{-60}{m} $$

Nunca se integra hasta el final (izquierda: la curva se desploma a −∞). Se trunca en el cruce con el ruido usando metodo_lundeby y se mide sobre el tramo lineal (derecha). RI sintética con T60 conocido · Spec · m3_producto_final.md §2–3 · Schroeder 1965.

- DOS graficos de la MISMA curva: completa (izq) y acotada (der). - Completa: se ve el codo (entra en el ruido) y el desplome a -inf al final de la integracion. Eso justifica truncar con Lundeby. - Acotada: se ve la regresion sobre el tramo lineal y la extrapolacion a -60 dB. De ahi sale el T60. - Schroeder es una linea: cumsum(h[::-1]**2)[::-1] / sum(h**2), luego 10*log10. - regresion_lineal implementada a mano demuestra que entienden minimos cuadrados. - Timing: 4 min.
M3 · función 04 · los parámetros ISO 3382

Tres tramos, tres parámetros.

Cada parámetro es una regresión sobre un tramo distinto de la curva de Schroeder. Todos se extrapolan a −60 dB.

ParámetroTramo de la curvaQué mide
EDT
Early Decay Time		0 a −10 dBPercepción subjetiva de la reverberación. Sensible a las primeras reflexiones.
T20−5 a −25 dBTiempo de reverberación con menos rango dinámico requerido. Útil con SNR limitado.
T30−5 a −35 dBEl estándar. Preferido cuando SNR > 45 dB. Es el que se reporta como T60.
En ningún caso se mide directamente un decaimiento de 60 dB — no hay rango dinámico para eso en una sala real. Siempre se mide un tramo corto y se extrapola con la pendiente. Todo se calcula por banda de octava.
- EDT usa el tramo inicial (0 a -10): captura la primera impresion auditiva. - T20 y T30 arrancan en -5 dB para saltear la reflexion directa. - T30 es el estandar salvo que el SNR no de (< 45 dB) — ahi cae a T20. - Nunca se mide -60 dB directo. Se extrapola. Punto clave conceptual. - Timing: 3 min.
M3 · el eje frecuencial · filtrado por bandas

Los parámetros acústicos se calculan banda por banda: primero se filtra la RI en cada octava (IEC 61260), y sobre cada banda filtrada se corre el pipeline Schroeder → regresión. Esto ya lo tienen de M2.

Detalle crítico que se arrastra a M3: usen sosfiltfilt (fase cero, forward + backward), nunca lfilter. El retardo de grupo de un filtro causal desplaza el inicio del decaimiento y les infla el T60 en graves un 5–15%.

Clase 9 · m3 reutiliza filtro_octava de M2 · frecuencias centrales IEC 61260 (125 Hz a 4 kHz para la tabla de validación).

- Nada nuevo respecto a M2 en el filtrado — se reutiliza filtro_octava. - Recordar sosfiltfilt (fase cero). Sin eso T60 en graves sale inflado. - El grafico sale de get_filter_response de la API de referencia. - Timing: 3 min.
M3 · el output final

Este es el producto final del análisis: los tres parámetros contra la frecuencia central de cada banda. Es lo que devuelve calcular_parametros_acusticos y lo que su API expone en /api/v1/acoustics/parameters/by-bands.

Acá se ve una sala real: la Usina del Arte, con T30 ≈ 2 s y la forma de campana típica (máximo en medios, caída en graves y agudos por absorción). A diferencia de la RI sintética de las slides 6–7 (donde EDT ≈ T20 ≈ T30), acá los parámetros se separan: cuando EDT supera a T30 hay reflexiones tempranas fuertes; las diferencias entre bandas son información acústica real de la sala.

ISO 3382 · el mismo gráfico que van a ver en el frontend de cátedra cuando suban su WAV. Sintética = enseñar el método (T60 conocido) · real = validar el producto.

- CAMBIO: ahora es una RI REAL (Usina del Arte, sala de conciertos de Buenos Aires, de OpenAIR). - Forma de campana: T30 max en medios (~2.2s), cae en graves/agudos. Tipico de sala real. - A diferencia de la sintetica, EDT/T20/T30 se SEPARAN. EDT>T30 = reflexiones tempranas. - Sintetica (slides 6-7) para enseñar el metodo; real aca para el producto. La consigna pide las 2. - Es el output de /acoustics/parameters/by-bands en su API. - Timing: 3 min.
M3 · validación · lo que separa un TP de un producto

No alcanza con que los tests pasen. Hay que demostrar que los números coinciden con un software profesional sobre RIs reales.

  • Al menos 2 RIs: una sintética y una real (OpenAIR)
  • Comparar contra REW, ARTA, Aurora o Dirac
  • Bandas 125, 250, 500, 1000, 2000, 4000 Hz

Criterio de aceptación

Los tiempos de reverberación (EDT, T20, T30) no deben diferir en más de ±0.5 s respecto de la referencia.

Si su pendiente da la mitad que la de REW, hay un bug — probablemente en el filtrado o en los límites de Schroeder.

Grupos con validación sólida: lúzcanla en la presentación. Una tabla RIR-API vs REW banda por banda con diferencias < 0.5 s es lo más convincente que pueden mostrar.
- El grafico de validacion usa datos de referencia ILUSTRATIVOS (script). En el informe real la columna "referencia" sale de medir la MISMA RI en REW/ARTA. - Criterio: +-0.5s en tiempos de reverberacion. - Tip de devoluciones: los grupos con buena validacion OpenAIR (Maes Howe, Hamilton) que la luzcan. - Timing: 3 min.
M3 · validación automática

Los tests, ahora también de la API.

M3 agrega tests de endpoints a los de las funciones. Cobertura mínima 80% en análisis + API.

Tests de análisis

  • suavizado — la envolvente no distorsiona la señal
  • Schroeder — primer valor 0 dB · monótona decreciente · RI con T60 conocido
  • regresión — R² = 1 para datos perfectamente lineales
  • parámetros — T30 dentro de ±10% de un T60 = 2.0 s conocido

Tests de API

  • /health responde 200
  • análisis de un WAV válido devuelve los parámetros
  • generación de pink-noise devuelve un WAV
  • archivo inválido → 422 (no un 500)

Con TestClient o httpx.AsyncClient. pytest --cov=app tests/ da el reporte.

De las devoluciones: un test que "pasa de casualidad" (indentado mal, o que esquiva la función rota) da falsa cobertura. Que cada test realmente ejercite la función.

- M3 suma tests de API a los de funciones. Cobertura 80% en analisis + API. - El test de 422 (no 500) es clave: validacion Pydantic manejando el error bien. - Advertencia real de devoluciones: tests que pasan sin ejercitar la funcion = falsa cobertura. - Timing: 3 min.

El informe, ahora en Markdown.

Cambio respecto de años anteriores: el informe final va en Markdown (.md), no en Quarto ni LaTeX.

¿Por qué?

  • Sin toolchain — nada de instalar LaTeX ni compilar. Escriben en cualquier editor.
  • Versionable — el informe vive en el repo (docs/informe.md) y viaja con el código.
  • GitHub lo renderiza solo — se lee directo en el navegador, con imágenes y tablas.
  • Foco en el contenido, no en pelear con el formato.
